# Deployment and rollback

## Release identity

Every deployment is tied to the immutable Git commit SHA. API and worker image tags and Web release prefixes also include the workflow run ID and attempt so rerunning a release cannot overwrite a prior candidate; ECS deploys only digest references. Web assets are copied under `releases/<sha>-<run-id>-<attempt>/` before the root HTML is swapped. Native builds retain their app version, build number, commit SHA, API contract version, and enabled feature-flag snapshot.

GitHub Code Security must be enabled before protecting `main` (GitHub Advanced Security is required for CodeQL on private repositories). Require every Verify job, including all JavaScript/TypeScript, Kotlin, and Swift SAST matrix entries, as branch-protection checks. CodeQL observes real Gradle and Xcode compilation for the native languages; Trivy, dependency audit, and Gitleaks remain separate required controls rather than substitutes for SAST.

## Server release

1. The protected release gate accepts only `main` and requires a successful Verify workflow for the exact commit SHA. Production additionally requires the unexpired acceptance marker produced by a successful staging release of that same SHA.
2. The protected environment assumes an AWS role through GitHub OIDC; static AWS keys are not used.
3. API and worker images are built for Linux arm64, scanned, signed by the registry workflow, and pushed to immutable ECR repositories.
4. The release workflow registers digest-pinned task-definition revisions without replacing the stable service.
5. A dedicated one-off migration task receives `MIGRATION_DATABASE_URL` as its `DATABASE_URL` and runs forward-compatible migrations inside the private subnets. Long-lived API and worker task definitions never receive the migration credential. The release fails if the task exits nonzero.
6. `scripts/deploy-ecs.sh` updates the services. ECS circuit breakers roll back a failed deployment automatically. Readiness requires the database, Redis, outbox, and runtime-secret configuration to be usable.
7. The staging acceptance job creates isolated `example.test` accounts, pairs them, changes care consent, exchanges and responds to a care request, pauses privacy, and disconnects. Staging data is non-production and is purged on the staging environment's retention/reset schedule; the test never targets production. Production promotion reuses the exact staging-accepted commit and performs non-mutating API/Web readiness checks.

Database migrations follow expand/migrate/contract. A release may add nullable columns, tables, indexes built concurrently, or dual-write code. Destructive schema contraction occurs only after the previous binary is no longer serving traffic and the rollback window has closed.

Before the first deployment, connect with the RDS-managed administrator and run `psql "$RDS_ADMIN_URL" --file infra/database/bootstrap-roles.sql`. The script securely prompts for separate migration and runtime passwords, creates fixed non-superuser roles, removes public database/schema access, and can be rerun for credential rotation. Set `MIGRATION_DATABASE_URL` to the `rafay_pair_migration` login and `DATABASE_URL` to `rafay_pair_runtime_login`, both with verified TLS. Each production migration then reapplies the explicit table and sequence grants to the NOLOGIN `rafay_pair_runtime` group; the runtime login receives no schema-migration or DDL authority.

Both production images download the official AWS commercial-region `global-bundle.pem` during the reproducible BuildKit build with an exact SHA-256 checksum. The bundle contains only self-signed RDS root CAs, is mounted read-only at `/app/certs/aws-rds-global-bundle.pem`, and is passed explicitly to `pg` together with `rejectUnauthorized: true`; endpoint hostname verification remains enabled for the API, one-off migration, and worker. `DATABASE_CA_CERT_PATH` is mandatory in production and Terraform fixes it to that image path. Review AWS RDS CA announcements before changing the pinned checksum: download over HTTPS, compare the published bundle, enumerate and validate every root, update both Dockerfiles together, rebuild/scan both images, and prove a verified connection before promotion. Never switch to `sslmode=require`, `rejectUnauthorized: false`, or a connection-string CA override to work around rotation.

To roll back, set `API_TASK_DEFINITION` and `WORKER_TASK_DEFINITION` to the last known-good revision ARNs and run `scripts/rollback-ecs.sh`. Do not reverse a migration unless a separately reviewed down migration is proven lossless; normally roll application code forward against the expanded schema.

The Secrets Manager runtime JSON must contain separate `MIGRATION_DATABASE_URL` (schema owner) and `DATABASE_URL` (least-privilege runtime role), plus `REDIS_URL`, `SESSION_PEPPER`, `EMAIL_TOKEN_PEPPER`, `DEVICE_TOKEN_ENCRYPTION_KEY`, `SMTP_URL`, `PLAY_INTEGRITY_GOOGLE_CREDENTIALS_JSON`, and complete APNs/FCM credentials. The worker uses the runtime `DATABASE_URL`; neither long-lived service receives `MIGRATION_DATABASE_URL`, and only the API receives the Play Integrity credential. `DEVICE_TOKEN_ENCRYPTION_KEY` is exactly 32 random bytes encoded as unpadded base64url. Protected automation passes the JSON through Terraform's ephemeral input and the AWS provider's write-only secret argument, so its value is excluded from plans and state; increment `runtime_secret_version` to rotate it.

ElastiCache uses a password-protected RBAC `default` user restricted to HMAC-keyed API rate-limit counters, the ticket, ticket-quota, and connection-lease key patterns, and the pair fanout channel pattern. Its command allowlist contains only atomic counter expiry, ticket consumption, Lua-backed sorted-set lease/quota operations, and pub/sub operations. Supply the same URL-encoded password in `REDIS_URL` and Terraform's ephemeral `redis_auth_token` input. The AWS provider receives it only through `passwords_wo`; increment `redis_auth_token_version` when rotating it. Neither password value is persisted in Terraform state.

Security-group egress is deny-by-default: the ALB can reach only API port 3000, while application tasks can reach only their PostgreSQL/Redis security groups plus public TCP 443 and encrypted SMTP submission on 465/587. APNs, FCM, AWS APIs, and the approved SMTP service use changing public address pools that cannot be represented safely as security-group IP allowlists, so those three narrowly port-scoped public rules carry reviewed Trivy exceptions. Plaintext SMTP port 25 and arbitrary outbound protocols remain blocked; provider hostname and certificate validation is mandatory at the client layer.

## Web release

`scripts/deploy-web.sh` uploads immutable assets first, keeps prior hashed assets available, publishes stable root assets, and replaces `index.html` last with no-cache headers. A complete prior release stays addressable under its immutable release prefix. Set `RELEASE_ID`, `WEB_BUCKET`, and `CLOUDFRONT_DISTRIBUTION_ID`, then run `scripts/rollback-web.sh` to atomically restore its stable assets, service worker, and HTML.

CloudFront routes `/v1/*` to the API ALB with caching disabled and all viewer headers, cookies, and query strings forwarded except `Host`; this preserves host-only browser cookies and WebSocket upgrades on one public origin. `Sec-WebSocket-Protocol` is forwarded for the `rafaypair.v1` plus one-time-ticket offer but must be redacted from edge and application logs; the ticket is never placed in a URL and only `rafaypair.v1` is echoed. A CloudFront Function rewrites only extensionless Web routes to `index.html`. API authorization failures are never converted to SPA responses. `PUBLIC_API_URL=https://<api_domain>` remains the native/operations origin. The separate `PUBLIC_WEB_ORIGIN=https://<web_domain>` lets the API issue same-origin browser WebSocket URLs based on the authenticated platform without redirecting native clients through CloudFront.

## Native release

iOS and Android signing runs only in protected environments. The staging environment holds a separate Apple Development certificate/profile and exports the non-production Staging configuration as a development-signed IPA installable on registered devices. Production holds the Apple Distribution material and restricted App Store Connect key, exports an App Store IPA, and validates it before any upload. `scripts/archive-ios.sh` validates and applies the monotonic workflow run number as `CURRENT_PROJECT_VERSION`, retains the archive, IPA, and dSYMs, and the workflow independently verifies the embedded signature and team.

Android CI always produces an installable debug/development APK. The staging and production protected environments each hold their stable internal/upload keystore and passwords; local staging builds without those values are intentionally unsigned and non-distributable. Release automation fails closed on missing key material, uses the monotonic workflow run number as the validated `versionCode`, produces `app-staging.apk` or production APK/AAB artifacts, verifies their signatures, and compares every signer with the protected `ANDROID_SIGNING_CERT_SHA256` value before retaining `mapping.txt`. Store uploads occur only for an explicitly requested production release. TestFlight and Play internal testing remain promotion gates before a staged public rollout.

Enroll production in Play App Signing so the protected CI keystore is an upload key rather than the store-distribution key. Keep its encrypted backup and recovery material in access-logged, two-person-controlled escrow outside the repository and CI; staging uses an unrelated key. For planned rotation, create the replacement through the store-approved key-upgrade/reset process, update the protected keystore, passwords, alias, and `ANDROID_SIGNING_CERT_SHA256` together, then require a signed internal-track build and exact fingerprint verification before removing the previous upload key. If the upload key is lost or suspected compromised, stop releases, revoke CI access, use the Play Console upload-key reset procedure, and retain the incident and fingerprint-change evidence. The Play-managed app-signing key is never exported into RafayPair infrastructure.

Configure `RAFAYPAIR_FIREBASE_APPLICATION_ID`, `RAFAYPAIR_FIREBASE_API_KEY`, `RAFAYPAIR_FIREBASE_PROJECT_ID`, and `RAFAYPAIR_FIREBASE_SENDER_ID` as real public Firebase client variables at repository level for the Verify release bundle and separately in each protected release environment for staging/production. Distributable Gradle tasks fail if any identifier is empty. These are app identifiers embedded in the APK, never an FCM service-account private key; restrict the Firebase API key to the expected Android package and signing certificate in Google Cloud.

Configure `RAFAYPAIR_PLAY_INTEGRITY_CLOUD_PROJECT_NUMBER` as a protected repository/environment variable for the Google Cloud project linked to the exact staging or production package in Play Console. Configure `PLAY_INTEGRITY_ALLOWED_CERTIFICATE_SHA256_DIGESTS` from the Play App Signing certificates (unpadded base64url, not the CI upload-key fingerprint) and `PLAY_INTEGRITY_MIN_VERSION_CODE` as the supported client floor in the same protected environment and Terraform inputs. The project number is embedded in the app; backend Google credentials remain only in Secrets Manager. Distributable Gradle tasks, release policy validation, and production API startup fail closed when their required identifiers, signer/version policy, or credentials are missing. Before promotion, install the signed build through its Play internal track on a certified physical device and retain one successful content-bound assessment audit; local sideloads and emulators are not production evidence. Full provisioning and response policy are in [Android Play Integrity](../security/android-play-integrity.md).

Configure `app_attest_team_id`, `app_attest_bundle_id`, `app_attest_allowed_validation_categories`, and `app_attest_allowed_bundle_versions` in each Terraform environment. Terraform derives the isolated development/production App Attest environment and injects the corresponding complete `APP_ATTEST_*` API policy. The protected iOS profile must contain the matching App Attest entitlement; release automation checks the signed application and profile values. Before promotion, verify initial attestation plus increasing assertions on a physical iPhone installed through the intended channel. Simulator and unsigned builds are expected to report unsupported and are not release evidence. Full key lifecycle, validation, and logging rules are in [iOS App Attest](../security/ios-app-attest.md).

Rollout order is internal, alpha, beta, then production. Production begins at the smallest supported cohort and expands only while crash-free sessions, startup, API errors, privacy-pause propagation, and scientific-safety telemetry remain within budget. Server contracts remain backward compatible for every supported native client version.
